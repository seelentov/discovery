# Диагностика Discovery

Начни с конкретного симптома: действие, ожидаемый и фактический результат, версия/commit, конфигурация и время. Отделяй подтверждённые факты от гипотез.

1. Воспроизведи в выделенном экземпляре по `discovery-run` или `discovery-e2e`. Не диагностируй старый встроенный UI: сначала проверь порядок frontend → Rust build.
2. Проследи путь по `AI_CONTEXT.md`: UI/REST → store/queue → handler → протокол → запись результата → выдача API. Для задержек проверь постановку, claim, ошибки/retry и доступность worker, а не только размер очереди.
3. Сопоставь логи одного экземпляра с ID устройства/задания и временными метками. Не выводи credentials, токены, полные конфиги или содержимое secret-полей.
4. При проверке storage установи фактическое подключение домена через `ConnectionRegistry` и конфиг. Memory storage теряется при рестарте; данные разных доменов могут быть в разных БД. Читай только необходимые записи.
5. Проверяй одну причинную гипотезу направленным экспериментом. Подозрение на race без воспроизведения не называй установленной причиной.
6. Исправление сопровождай тестом, который воспроизводит исходный сбой, затем регрессией по `discovery-test`. Отчёт: причина/доказательство, изменение, проверки; если причина не доказана — чего именно не хватает.

Если стенд отсутствует, ограничь выводы наблюдаемым уровнем. Не подменяй реальный протокол mock-ответом без явной отметки.
