# Запуск Discovery

Работай из выделенного worktree. Команды ниже для shell macOS/Linux; для Windows см. корневой `QUICKSTART.md`.

1. В `crates/web/frontend`: `npm ci`, `npm run build`.
2. В корне: `cargo build -p discovery-agent --locked`.
3. Выбери свободный loopback-порт, отдельный рабочий каталог и файл конфигурации. Не используй корневой `config.toml` вслепую: он может ссылаться на общие базы.
4. Минимальный конфиг для временного экземпляра:

```toml
[server]
addr = "127.0.0.1:18088"
[logging]
file = ""
```

Без storage данные в памяти. Для проверки перезапуска добавь SQLite с отдельным абсолютным `file_path` по образцу `QUICKSTART.md`.

5. В окружении процесса установи `CONFIG_FILE` в абсолютный путь к этому конфигу и `DISCOVERY_BOOTSTRAP_ADMIN_PASSWORD` в уникальный пароль (минимум 8 символов). Если нужны секреты протоколов — `DISCOVERY_SECRET_KEY`, Base64 от 32 случайных байт. Не выводи значения в отчёт.
6. Запускай абсолютный путь `<worktree>/target/debug/discovery-agent` из выделенного рабочего каталога. Сохрани PID и вывод именно своего процесса.
7. Проверь, что процесс жив и `GET /` выбранного порта возвращает UI; затем реальный вход. Сообщение `dashboard listening` печатается до bind и само по себе не подтверждает готовность.
8. Останови только свой процесс через SIGTERM/управляемую terminal session; проверь освобождение порта. Не используй общий `pkill discovery-agent`.

Для браузерных проверок предпочитай существующий Playwright setup: он сам создаёт конфиг, credentials и процесс. Не запускай второй сервер на его порте. Установку из бинарника, Docker и systemd см. в `QUICKSTART.md`.

## Актуальность запущенной сборки

`npm run build` создаёт `crates/web/frontend/dist`; RustEmbed в `crates/web/src/lib.rs` включает его в сборку. `crates/web/build.rs` отслеживает изменения `frontend/dist` через `rerun-if-changed`. Поэтому после изменения UI нужны обе сборки в указанном выше порядке и перезапуск процесса: уже работающий сервер не обновится от замены бинарника.

Проверяй код завершения каждой сборки. Зафиксируй путь запускаемого бинарника и PID своего процесса. После перезапуска сравни ссылки на JS/CSS в `GET /` с текущим `dist/index.html` и проверь изменённое поведение. Ответ Vite dev server не подтверждает обновление встроенного UI. Если сборка не подхватила `dist`, сначала проверь worktree, target-каталог и путь процесса; не начинай с полного `cargo clean`.
