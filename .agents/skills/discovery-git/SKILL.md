# Git и параллельная работа

1. Проверь `git status --short`, `git branch --show-current`, `git worktree list`. Зафиксируй базовый commit и границы задачи в чате.
2. Используй выделенный worktree этого чата или создай новый на согласованной базе. В обычном shell: `git worktree add -b codex/<slug> <новый-путь> <base-ref>`. В Codex managed worktree используй инструменты приложения, затем создай ветку `codex/<slug>`, если checkout detached. Не предполагай наличие незакоммиченных файлов основного checkout в новом worktree.
3. Не дели БД, runtime-конфиг, порт, target-каталог и E2E auth-каталог между параллельными задачами. Изменения документации в другом репозитории требуют отдельного worktree и commit там.
4. Перед commit проверь `git diff --check`, `git diff --stat`, содержимое изменённых файлов и новые файлы. Не включай `.env`, credentials, базы, логи, build/test artifacts и чужие изменения.
5. Добавляй конкретные пути через `git add -- <paths>`, проверь `git diff --cached`, затем сделай локальный commit. Это разрешено без дополнительного вопроса. В сообщении опиши конкретный результат.
6. Отчёт: SHA, ветка, путь worktree, проверки и ограничения. Сохраняй worktree для просмотра результата; не удаляй нужные пользователю untracked/ignored артефакты.

Push и merge в `main` требуют явного указания пользователя; запрос «реализуй» этого не означает. При разрешённом push проверь remote и точную ветку. Не делай force-push по умолчанию. Не выполняй merge вместо публикации ветки.
