# Discovery — инструкции для ИИ

Независимая система мониторинга сетевых устройств на Rust для региональных провайдеров.
AggreGate — архитектурный ориентир, а не часть этой кодовой базы. Применимость его решений проверяй по задаче.

## Работа по запросам

- Источник задачи, согласованных границ и отчёта — текущий чат. Файлового backlog, task-файлов и диспетчера нет.
- Перед изменениями проверь ветку и `git status`. Каждую задачу с изменениями выполняй в отдельном worktree и ветке `codex/<slug>`; подходящий worktree этого чата можно продолжать использовать.
- Сохраняй чужие изменения. Параллельным задачам нужны отдельные порты, БД, конфиги, процессы и тестовые артефакты.
- Локальный commit разрешён без вопроса: включай только изменения задачи. Push и merge в `main` выполняй только по явному указанию пользователя.
- Не создавай новую задачу в другом чате без запроса. Дополнительные находки кратко сообщай в текущем чате.
- Проверяй предпосылки задачи по коду и наблюдаемому поведению. При расхождении сообщай конкретные факты; уточняй дальнейшие действия, если это меняет согласованный результат. Уточняй неоднозначность, влияющую на результат; обычные технические решения принимай самостоятельно.
- Ответы и вывод инструментов — краткие. Итог: результат, проверки, ограничения, commit и расположение worktree.

## Экономия контекста

- Для поиска используй `rg` и `rg --files`; если они недоступны — `grep` и `find`. Ограничивай поиск нужными каталогами, типами файлов и контекстом совпадений (`-n`, `-A`, `-B`).
- Длинный вывод сборок, тестов и диагностики (stdout и stderr) сохраняй в отдельные временные файлы задачи. В контекст выводи итог, ошибки и относящиеся к ним фрагменты; полный лог читай по необходимости.
- Сохраняй и проверяй код завершения исходной команды, не подменяя его кодом фильтра или `tee`. Отсутствие совпадений при фильтрации не означает успешную проверку. Для тестов проверяй итоговые счётчики и детали падений, а не только строки со словом `error` или последние строки лога.
- Для JSON используй `jq` с выбором нужных полей. Не выводи целиком большие ответы API, дампы и минифицированные файлы, если для задачи достаточно отдельных фрагментов.
- Не запускай повторно дорогую команду только ради другого представления вывода: анализируй сохранённый результат. Временные логи и диагностические артефакты не включай в commit.

## Краткая архитектура

- `crates/agent/src/main.rs` — запуск и связывание сервисов; `crates/core` — общие типы и контракты.
- `crates/web/src/lib.rs` — REST и раздача UI; `crates/web/frontend` — React, встраиваемый в бинарник.
- `crates/db`, `crates/entities`, `crates/migration` — подключения, сущности и схема; `crates/config-store` — хранение настроек и профилей.
- Остальные подсистемы и связанные места изменений см. в `AI_CONTEXT.md`; читай нужную область, не весь проект.

## Код и документация

- Пиши комментарии в коде на английском; объясняй причины, ограничения и нетривиальные решения, не пересказывай очевидные имена и действия.
- Текущее поведение проверяй по коду. [AI_CONTEXT.md](AI_CONTEXT.md) — карта для навигации, читай по необходимости.
- [QUICKSTART.md](QUICKSTART.md) — запуск с нуля, также включается в Linux-пакеты.
- Готовые бинарники публикуются в GitHub Releases этого репозитория; публикация требует явного запроса.
- Пользовательская документация — в `docs/` этого репозитория. При изменении пользовательского поведения обновляй соответствующие разделы в том же commit/ветке.
- Проект распространяется под Apache-2.0 (`LICENSE`).
- Сейчас поддерживаем чистую установку. Перенос данных старых версий и обратная совместимость схемы не требуются. Существующий механизм создания схемы (`crates/migration`) не удаляй по этой причине.
- Не восстанавливай удалённые инструкции и стенды без запроса. Не читай и не публикуй содержимое `.env`, ключи, пароли и тестовые credentials без необходимости.

## Обязательные проверки

- 100% нового функционала должно быть покрыто Unit и E2E: каждый новый сценарий, ошибки и граничные случаи. Покрытие строк не заменяет проверку поведения.
- Для исправления ошибки добавь регрессионную проверку исходного сбоя. Изменения существующего поведения также проверяй на обоих уровнях.
- Во время разработки начинай с точечных проверок затронутого поведения; команды см. в `discovery-test` и `discovery-e2e`. Перед завершением выполняй обязательные полные проверки.
- Запускай новые и существующие тесты для выявления регрессий: `cargo test --workspace` и полный Playwright-набор. Для фронтенда также `npm run build` и `npm run lint`.
- До Rust-сборки собери UI: в `crates/web/frontend` выполни `npm ci`, затем `npm run build`. UI встроен в бинарник.
- Игнорируемые live-тесты не входят в обычный Cargo-прогон. Затронутые сценарии запускай отдельно при наличии стенда. Отсутствующий стенд или ОС отмечай как непроверенный уровень, а не успех.
- Не объявляй поведенческую задачу завершённой, пока обязательные проверки не прошли. Не скрывай существующие падения, не ослабляй assertions ради зелёного прогона.
- Для изменений только документации/инструкций не запускай продуктовые тесты. Для сборочных изменений выполняй относящиеся к ним проверки. В отчёте отдельно укажи Unit/E2E и причины неприменимости или блокировки.
